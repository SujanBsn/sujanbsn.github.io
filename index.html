INTERFACE IMPLEMENTATION

Contest flow, player data,
and gameplay in one UI.

I implemented a main menu with round navigation, contest details, player profiles, settings, and tutorial pages. The leaderboard interface creates rank rows, loads country flags, highlights the current player, and presents their personal entry.

The interface waits for contest, leaderboard, player, and configuration data before initializing. Once it is ready, data-change events keep the display in sync with the shared state.

  • Three round leaderboards and contest information
  • Current-player highlight and personal rank or qualification state
  • Profile and flag presentation across the interface
  • Audio settings and tutorial pages with video demonstrations
LeaderboardUIHandler.cs · PlayerUIHandler.cs · ContestUIHandler.cs · TutorialHandler.cs
GAMEPLAY + STATE + LIFECYCLE

Coordinate collisions,
loading, and responses.

Dedicated behaviours handle launching, spawning, collision processing, merging, and game flow. ScriptableObjects hold shared configuration and state, while custom event channels connect gameplay responses.

The combination handler queues collision pairs, checks for duplicate pair keys, and prevents vegetables from entering multiple merges at once. Loading phases coordinate Firebase and configuration readiness before the wider interface proceeds.

  • Separate behaviours for core gameplay responsibilities
  • Queued merge processing and duplicate-pair checks
  • Shared configuration for tiers, physics values, and progression
  • Listener cleanup and version checks that ignore stale callbacks

LeaderboardScriptableObject sorts entries and broadcasts changes. LeaderboardUIHandler responds by rebuilding rows, downloading country flags, and updating the current-player presentation.

READINESS + RUNTIME GENERATION

Prepare the data.
Build the board.
Begin the game.

Content preparation populates WordListObject before activating gameplay initialization. InitializeGame shuffles the combined letters, creates answer slots based on word length, and spawns letter tiles within the board regions.

A loading scene adds the main scene asynchronously, waits for the answer boxes, letter boxes, and image to be ready, then starts the game and unloads itself.

  • Shared word, status, clock, score, and input-checking data
  • Generated board elements driven by the selected words
  • Explicit readiness flags coordinate initialization
  • Separate loading, gameplay, tutorial, and result scenes

ORIGINAL FIRESTORE CONTENT PIPELINE

Connect content records
to game-ready data.

The retained Firestore implementation queries active image records by category, selects image metadata, and retrieves the corresponding word document. Image URLs are used to download textures with UnityWebRequest and create sprites.

Candidate words are normalized and checked before four words are assigned to the shared word data. The selection flow includes capped retries and a return-to-menu path when preparation fails.

  • Category and active-status filters on Image_Repo
  • Associated Word_Repo document lookup by image ID
  • Asynchronous image download and sprite assignment
  • Content checks before gameplay initialization
Demo configuration

The supplied build and recording use a local sample-word pool. The original Firestore methods remain in the project, but the demo startup bypasses database queries and image downloads.

One board.

Answer checking maintains candidate words for each answer region, identifies valid assignments, checks whether a word is already used, and updates the remaining candidates. Input behaviours handle tile selection, placement, and swapping according to the current mode.

  • Mode-dependent input and answer-locking rules
  • Separate mode clocks and score data
  • Custom events carrying sender and response data
